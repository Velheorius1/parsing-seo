## Находка №1 (главная) — «UZEX Обратные аукционы»: 100% битых deep-ссылок, две подсистемы UZEX с пересекающимися id

Шаблон `https://xarid.uzex.uz/auction/detail/{id}` открывает **чужой лот из 2021 года**. Проверено в браузере:

| id из нашей БД | Что в БД | Что реально открывается |
|---|---|---|
| 1128 | «Текстиль и изделия текстильные», 2 500 000 сум | лот `21121007001128` «Продукты минеральные», 1 493 830 сум |
| 1134 | «Машины и оборудование…» , 20 000 000 сум | лот `21121007001134` «Стеновые панели» (алюкобонд), 7 312 340 сум |
| 808 (из живого API) | «Изделия резиновые и пластмассовые», 16 000 000 сум | лот `21121007000808` «Сооружения и стройработы», 955 000 сум |

**Корневая причина найдена.** У UZEX два независимых аукционных бэкенда, и их пространства id пересекаются:

| Бэкенд | Пример | displayNo | UI |
|---|---|---|---|
| `xarid-api-auctionx.uzex.uz/api/Lot/GetList` — **наш источник** | id=808 | `2611**1131**000808` | **не найден** |
| `xarid-api-auction.uzex.uz/Common/GetMinimizedLotsList` — питает `xarid.uzex.uz/auction` | id=408965 | `2611**1007**408965` | `xarid.uzex.uz/auction/detail/408965` ✅ |

Сегмент 4 знаков в displayNo (`1131` vs `1007`) — это разные торговые площадки. Мы тянем данные из площадки 1131, а ссылаемся в UI площадки 1007, где под теми же короткими id лежит архив 2021 года.
Ссылка не просто «не открывается» — она открывает **другой настоящий лот**, что хуже 404: по ней можно посчитать цену не того тендера.

Роут UI для auctionX не найден (проверено 4 кандидата): `new-xarid/home/auction/detail/{id}` → 404, `new-xarid/home/auction/list/main` → 404, `xarid.uzex.uz/auction/detail/{displayNo}` → пустая карточка, `xarid.uzex.uz/auctionx/detail/{id}` → сброс на главную.
Данные лота при этом доступны анонимно: `GET xarid-api-auctionx.uzex.uz/api/Lot/Get?id=808` → 200 + полная карточка. Значит UI почти наверняка существует, его надо найти (вероятно, требует авторизации в кабинете).

**Что применено:** только предупреждающий комментарий в `crawler/config/sources.yaml` (пометка «STALE — do not trust», разбор причины, контр-примеры). Комментарий от 2026-06-21 «browser-verified» теперь ложный и вводит в заблуждение — следующий агент не должен на него опереться. Поведение не изменено, YAML провалидирован.
**Что НЕ применено (решение Данияра):** смена `source_url_template`. Замену нельзя верифицировать браузером → по правилу ШАГ 7 это рискованная правка.

## Находка №2 — cooperation.uz: ссылка из Telegram не работает с телефона

SPA `new.cooperation.uz` жёстко редиректит на `mobile.cooperation.uz`, если `window.innerWidth <= 768` **или** User-Agent мобильный. Код в бандле `index.6hzd6WSl.js`:

```js
jM = 768;
e = () => { o.value = window.innerWidth <= jM || wM.test(navigator.userAgent) }
r = () => { o.value && (window.location.href = "https://mobile.cooperation.uz") }
```

Наблюдалось вживую: открытие `new.cooperation.uz/supplier/lots?lotId=SL1573737` увело на лендинг мобильного приложения. При этом `mobile.cooperation.uz/supplier/lots?lotId=SL1573737` → **404**, то есть на мобильном домене роута лота нет вообще.

Практический смысл: Данияр читает алерты в Telegram **с iPhone** → мобильный UA → все ссылки Cooperation.uz ведут на рекламу приложения, а не на лот. Для десктопа ссылки, по-видимому, рабочие (сервер отдаёт 200 и SPA-оболочку) — но это не тот путь, которым лоты реально открывают.
Cooperation.uz — 4 из 12 позиций в precision-выборке этой недели, то есть заметная доля потока.

**Кандидаты на фикс (не применял):** (а) добавить номер лота `SL…` в текст алерта, чтобы его можно было найти поиском на портале; (б) найти deep-link мобильного приложения; (в) слать десктопную ссылку с явной пометкой «открывать с компьютера». Требует решения Данияра — это правка шаблона алерта, а не источника.

## Идеи улучшений (ШАГ 4)

> Отклонение от процедуры: `/deep-think` в штатном виде разворачивает 5-10 параллельных агентов, которые заново читают тот же репозиторий. Это ровно тот случай, который запрещён инвариантом «Read/Grep напрямую; агенты-исследователи — крайняя мера» (инцидент «200k на исследование»). Анализ проведён по прочитанному коду напрямую.

**1. Верификатор ссылок должен сверять ЛИЧНОСТЬ лота, а не факт существования** (эффект: закрывает весь класс `wrong_card`).
`crawler/core/verifier.py` спрашивает у API источника «жив ли лот» — и для находки №1 честно отвечает «жив». Открывает ли `source_url` именно **этот** лот, не проверяет никто, кроме ручной браузер-выборки n≈6-9 раз в неделю. Поэтому источник со 100% битых ссылок жил незамеченным ≥5 недель.
Фикс: детерминированный `link_identity_check` — по id из `source_url` дёрнуть detail-endpoint и сверить `displayNo`/`startCost`/`categoryName` со строкой БД.
Проверяемо: на `uzex-auctions` ожидаем ~0/20 совпадений, на `uzex-prequest` ~20/20. Расхождение метрики с этим предсказанием = баг в чекере.

**2. Найти UI-роут auctionX** (эффект: link_integrity 7.8 → ~8.7, композит +0.22; плюс снимается риск «посчитал цену не того лота»).
Точка входа известна: `xarid-api-auctionx.uzex.uz/api/Lot/Get?id={id}` работает анонимно. Нужен вход в кабинет xarid.uzex.uz и клик по живому обратному аукциону — 5 минут вручную. Проверяемо: открыть найденный роут для id=808 → должен показать displayNo `26111131000808`, 16 000 000 сум, Андижанская обл.

**3. Cooperation.uz — номер лота в текст алерта** (эффект: ~17% алертов перестают быть тупиком на телефоне).
Самый дешёвый из трёх кандидатов: не требует знания мобильного роута, работает при любом поведении SPA. Проверяемо: в алерте есть строка `SL1573737`, поиск по этому номеру на портале открывает лот.

**4. Декомпозировать провал recall** (эффект: отделяет «умершие источники» от возможной регрессии фильтра — сейчас это одна цифра 5.8 без диагноза).
Посчитать alerts по источникам W30 vs W31, вычесть вклад 7 умерших источников и 8 мьютов. Проверяемо: если остаток ≈0 — платформа просто просела по источникам, чинить надо их; если остаток велик — регрессия в фильтре/AI-пороге, и это приоритет №1 следующей недели.
