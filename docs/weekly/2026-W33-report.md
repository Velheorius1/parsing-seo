### 2. Суточный снапшот падал ТРЕТЬЮ неделю подряд — обе прошлые правки лечили симптом

Прогон `metrics_tracker --save` в 02:00 10.08 упал ровно как в W32:

```
02:00:17 [WARNING] tenders offset=76000 failed (attempt 3/4): 57014 statement timeout — retrying with page=125
02:00:29 [ERROR] tenders offset=76000 page=125 failed after 4 attempts
postgrest.exceptions.APIError: 57014
```

Снапшота за 10.08 не было (`metrics.jsonl` последняя запись — 09.08 00:11).

**Корень:** множество активных источников (≤110 строк-имён) добывалось вычиткой **всех 90 328 строк** недельного окна — 90 страниц с растущим OFFSET. Цену страницы задаёт OFFSET, а не LIMIT, поэтому уполовинивание page из фикса `742807b` (03.08) не помогает: страница упала на 1000, 500, 250 и 125. Вторая правка (`_get_count`, 04.08) чинила счётчики — другой участок того же маршрута. Оба раза лечился симптом.

**Применено** (`1fc89ce`): то же множество берётся индексным `limit(1)` на каждый источник — имена уже известны из `source_counts` (all-time надмножество недельного), вопрос сводится к «есть ли хоть одна строка за неделю». Результат идентичен по определению; падение отдельной пробы не валит снапшот и логируется WARNING.

**Верификация на проде (не рассуждение):** прогон 05:53–05:56 дошёл до конца, `Snapshot saved`, `metrics.jsonl` обновлён 05:56. Активных 82 / мёртвых 28 — **совпало со снапшотом 09.08** (82 / 28), то есть замена эквивалентна. Шаг активных источников: 05:56:19 → 05:56:39 ≈ 20 с вместо падения после минут ретраев. `weekly_metrics` после этого сравнивает 03.08 → 10.08 (ровная неделя), а не 03.08 → 09.08.

**Следующая бомба на том же маршруте, НЕ тронута:** шаг 2 (`source_data = _fetch_all(client, "tenders", "source")` без фильтра) вычитывает **все 740 242 строки** таблицы — 740 страниц deep-OFFSET, 3 мин 11 с из 3 мин 52 с общего времени. Сейчас проходит, но растёт вместе с таблицей и упрётся в тот же timeout. Правка требует брать список источников из `sources.yaml` + прошлого снапшота (иначе новый источник исчезнет из метрик) — это смена семантики, вынесено на решение, не применено (инвариант «один баг за раз»).

## Идеи /deep-think

Проведён без фан-аута агентов (инвариант «200k на исследование»), на данных ШАГ 1–2.5.

1. **Мерить link integrity через тот же прокси, что и ингест.** 63% ссылок алертов недоступны из среды рутины, значит 25%-й sub-score сейчас про хвост. Прямая проба HTML не годится — проверено: `new-xarid` отдаёт SPA-скелет, одинаковые 15 408 байт для разных лотов, id в HTML нет; `new.cooperation.uz` — 852 байта. Рабочий путь: спрашивать те же API, что и адаптеры (`xarid-api-prequest.uzex.uz/api/Public/GetLots`, `xarid-api-shop.uzex.uz/Common/GetOffersList`) через `RESIDENTIAL_PROXY_URL` и проверять, что id алерта присутствует в живой выдаче с тем же заголовком. Проверяемый эффект: link integrity считается по ≥90% доставленных ссылок вместо ~30%.
2. **Дедуп зеркал XT-Xarid ↔ Hayotbirja по `Лот идентификатори`.** Замер: 190/190 пересечение, 9 дублей-алертов за неделю. Проверяемый эффект: −9 алертов/нед. дублей, recall перестаёт надуваться.
3. **Разобрать регрессию p95 11 006 → 15 623 мс (+42%)** при падении числа вызовов 615 → 508. Меньше вызовов, но медленнее — похоже на смену состава лотов (длинные мульти-позиционные) либо на деградацию апстрима. Проверяемый эффект: cost sub-score 7.1 → ~8.5, если p95 вернуть под 11 с.
4. **Закрыть вторую бомбу deep-OFFSET** (шаг 2, 740 тыс. строк, 3 мин 11 с). Проверяемый эффект: снапшот с ~3 мин 52 с до ~40 с и перестаёт зависеть от роста таблицы.
