## Находка №1 (главная): 4 месяца тихой потери данных — фетч работал, запись падала

`Cooperation.uz Контракты` числился мёртвым источником и кандидатом на prune, хотя
апстрим всё это время отдавал ~198 свежих контрактов на каждом прогоне.

**Корень.** `scripts/fetch_cooperation.py:upsert_to_supabase()` не дедуплицировал
строки внутри батча. Апстрим `stat-new.cooperation.uz/auction-contracts` стабильно
отдаёт один повторяющийся `external_id` — `coop-contract-MAB1000028` (198 строк /
197 уникальных). Postgres на такой батч отвечает `21000 ON CONFLICT DO UPDATE
command cannot affect row a second time` и откатывает **весь** батч целиком.

**Доказательство из прода** (не рассуждение): в `/var/log/parsing-seo-proxy.log`
8 из 8 последних проб содержат ровно один дубль ключа, и следом
`[AucContracts] Upserted: 0 / 196`. Ошибка повторяется **358 раз с 02.04.2026**,
сейчас 2–6 раз в сутки. Последняя записанная строка источника — **09.06**.

**Почему это не было видно.** Прогон завершается словами `=== DONE: upserted 0,
new 81 ... ===` — «new 81» считается до записи, поэтому лог выглядит рабочим.
Источник тихо переезжает в dead → в prune-кандидаты, и три недели подряд
рутина докладывала его как «мёртвый», хотя данные были доступны.

**Что применено** (`3a4eb7c`, запушено в main, VPS подтянул): дедуп по
(external_id, source) с сохранением последнего вхождения — ровно то, что
`crawler/core/db.py:211-216` уже делает перед своим апсертом. Здесь этот шаг
просто отсутствовал.

**Верификация — двойная:**
1. Стаб-тест, воспроизводящий правило Postgres. На коде ДО фикса — `upserted: 0`
   (та же ошибка 21000, что в проде). На коде ПОСЛЕ — `195/196`, и здоровый путь
   без дублей не тронут: 1200/1200 через несколько батчей.
2. **Реальный прогон через резидентный прокси 11:27**: `Got 198 items` →
   `[Upsert] Deduplicated 198 → 197` → `UPSERTED: 197`. В базе
   `Cooperation.uz Контракты`: **115 → 197 строк**, свежесть 09.06 → 17.08.

**Тот же класс бага остаётся в двух местах** (латентно, срабатывает только при
дубле в апстриме): `crawler/scripts/fetch_ebirja_contracts.py:392` и
`scripts/fetch_uzex_auctions.py:292` — свои копии `upsert`, без дедупа.
`crawler/core/results_tracker.py` дедуп имеет. НЕ трогал: правило «один баг за
раз», и дубли там сейчас не наблюдаются — сначала нужен детектор (см. идею 2).

## Находка №2: platform_health наказывает за гигиену

Из 4 источников, «умерших» за неделю, **три отключены осознанно 05.08**, с
разбором прямо в конфиге:

| Источник | Причина отключения (из `sources.yaml` / `run_proxy_fetch.sh`) |
|---|---|
| `Ebirja Аукционы` | дубль `ebirja-auctions-active`; id брался ПОЗИЦИЕЙ строки (в базе `0..11`) → повторные алерты и вечно-невидимые новые лоты |
| `E-Birja встречный аукцион (листинг)` | тот же позиционный id; биржевое табло спот-цен без заказчика и срока — 0 алертов за 4 месяца |
| `Cooperation.uz Закупочные планы` | эндпоинт заморожен площадкой с 03.02; живой близнец `cooperation-plans-filtered` работает |

Четвёртый — `TG: Box Maker Tashkent`, просто тихий канал (последний пост 07.08).

`total_sources` в `metrics_tracker.py:208` = число РАЗЛИЧНЫХ значений `source`,
когда-либо попадавших в таблицу. Источник, once написавший хоть строку, остаётся
в знаменателе навсегда. Значит осознанное отключение мусорного фида **никогда**
не может улучшить platform_health — только ухудшить: 20% оценки монотонно
дрейфуют вниз по мере чистки. Это дефект метрики того же рода, что переопределение
FP в W30.

**НЕ применял.** Правка знаменателя ломает сравнимость с W25–W33 → решение Данияра.
Варианты: (а) исключать из знаменателя источники с `enabled: false`;
(б) отдельный счётчик «retired» рядом с «dead».

## Идеи (/deep-think) — 3 проверяемых улучшения

**1. Детектор тихих отказов записи: `fetched > 0 && upserted == 0`.**
Именно этот сигнал 4 месяца лежал в логах открытым текстом и никем не читался;
`freshness_watchdog` его не ловит, потому что смотрит на `collected_at`, а не на
результат записи. Проверяемо: прогнать детектор по историческим логам — он обязан
подсветить `AucContracts` начиная с 02.04. Эффект: класс «фетч жив, запись мертва»
перестаёт жить месяцами. Самая дешёвая из трёх.

**2. Prune-кандидаты должны отличать «апстрим пуст» от «мы не смогли записать».**
`Cooperation.uz Контракты` недели висел в списке на отключение, будучи полностью
живым. Достаточно приписывать каждому кандидату последний известный
`fetched`-счётчик: `dead, но fetched=198` — это баг, а не кандидат на prune.
Проверяемо: после правки контракты обязаны исчезнуть из списка, а 11 подфидов
Cooperation — остаться.

**3. Точность: усилить негативные примеры, а не строить regex-фильтр.**
Три из пяти FP недели — дословные пункты NOT-листа («папка», «закупка готовых
книг», «наружные баннеры»). Костыль-фильтр по подстрокам здесь запрещён правилом
про рельсы; правильный ход — добавить эти три случая в playbook как few-shot
негативы и померить на том же наборе. Проверяемо: прогнать 60 последних алертов
до и после, precision должна вырасти без падения recall. **Требует прогона на
7 днях — не применял.**
