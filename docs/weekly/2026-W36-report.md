## Находка №1 — два фида ETender молчали 12 дней: API перешёл на 1-based нумерацию строк

**Что произошло.** `ETender UZEX` и `ETender Обсуждения` не записали НИ ОДНОЙ строки с 19.08 по 31.08 (12 дней). Каждый прогон краула (раз в 2 часа) писал в лог:

```
[WARNING] crawler.adapters.base: [ETender UZEX] Error: Client error '400 Bad Request'
          for url 'https://apietender.uzex.uz/api/Common/TradeList'
```

**Корень (замер на живом API, не гипотеза).** Хост и доступ ни при чём — соседние эндпоинты того же хоста работали всё это время (`DealsList` 249 строк, `NotDealedList` 501). Поехал контракт именно этих двух: API перешёл на **1-based** нумерацию строк (в ответе `rn` начинается с 1), и `from=0` стал отвергаться:

```
{"status":400,"message":"ORA-20001: Sahifa chegaralari noto'g'ri
 ORA-06512: at \"PROPOSAL.FRONT_APP\", line 275"}
```

Перебор payload'ов по живому API — важно, что дело не в имени параметра, а именно в первой строке:

| payload | ответ |
|---|---|
| `{"from":0,"to":500}` (наш) | **400** |
| `{"from":1,"to":500}` | **200**, 500 строк, `total_count` 627 |
| `{"from":501,"to":1000}` | 200, 127 строк |
| `{"page":1,"limit":50}`, `{"PageNumber":1,...}`, `{"skip":0,"take":50}`, `{"System_Id":0}`, `{}` | 400 (все) |

DiscussionTradeList — то же самое: `from=0` → 400, `from=1` → 143 строки.

**Цена.** 770 лотов (627 + 143) вне видимости. Это ровно те два фида, которые W33 расчехлил вручную как ценные («ETender Обсуждения» — 4 из 4 алертов профильные: печать учебников ТГЭУ, юбилейный значок, картхолдеры Mastercard).

**Детекторы сработали — реакции не было 12 дней.** `freshness_watchdog` писал «ETender UZEX — 13730 rows, silent 10d», `funnel_watchdog` — «ТРЕВОГА: источник замолчал в алертах (было 21, стало 0)». Оба РЕАЛЬНО шлют в Telegram (`_send_telegram`), то есть сигнал доходил до владельца. Разобран механизм, почему он всё-таки потерялся:

- **Порог 7 суток.** `SILENCE_DAYS = 7` (`freshness_watchdog.py:42`) — первое сообщение физически не могло уйти раньше ~26.08, то есть неделя потери проходит вообще без сигнала.
- **Оповещение edge-triggered, без повторов и эскалации.** `new_silent = [s for s in silent if s["source"] not in prev]` (строка 259) — Telegram уходит ТОЛЬКО в тот день, когда источник впервые пересёк порог. Дальше источник лежит в state `freshness_watchdog_state`, и сколько бы недель он ни молчал, повторов нет. Подтверждено логами 29/30/31.08: строки «silent 9d / 10d / 11d» идут БЕЗ маркера `[NEW]` — то есть сигнал уже отработал один раз и замолчал навсегда, пока источник оставался мёртвым.
- **Ноль неотличим от нормы.** Сводка прогона печатает `etender: 0` в ряду из 60 источников; HTTP 400 логируется как `WARNING` и не влияет на код возврата прогона.

Итог: за 12 дней потери — одно сообщение на 7-й день, в общем потоке. **Это третий инцидент одного класса за три месяца** (W34 «фетч жив, запись мертва» — 4 месяца тихой потери; W35 «обогащение живёт до следующего краула и рапортует успех»). Общее у всех трёх: сигнал был, действия не было.

**Применено** (`9490bf5`): `offset_start` добавлен как опция пагинации, default 0. При 0 диапазон остаётся половинным `[from, from+size)` — байты запроса остальных 19 offset-источников не меняются; при 1 — включающий `[from, from+size-1]`. Опция выставлена ТОЛЬКО у `etender` (проверено: `offset_start set on: ['etender']` из 127 источников).

**Верификация двойная** — не по логу, а по базе (урок W34/W35: лог рапортует успех, база пуста):
- прод-прогон 16:03–16:07: `etender: 627 tenders`, `etender-discussion: 143` (было 0/0), `770 fetched, 729 new, 770 upserted, 6 alerts`;
- **чтением из базы:** `ETender UZEX last=2026-08-31T16:05 rows_last_hour=627`, `ETender Обсуждения last=2026-08-31T16:03 rows_last_hour=143`. Свежесть 19.08 → 31.08;
- 6 алертов ушло (seq #8146–#8151) + 2 в дайджест; `[ZeroResult] 0 alerts, 2 recoveries` — трекер сам зарегистрировал восстановление обоих источников.

## Находка №2 — recall штрафует за намеренный вырез шума

Падение алертов 385→258 разложено по источникам и по суткам:

| Блок | W35 | W36 | Δ | Природа |
|---|---|---|---|---|

| ETender UZEX + Обсуждения | 12 | 0 | −12 | наш баг (Находка №1, починен) |
| TG: PR Media Group | 96 | 71 | −25 | объём апстрима (301→249 строк) |
| UZEX Предквалификации | 65 | 43 | −22 | объём апстрима (4341→3346 строк) |
| остальное | 120 | 120 | 0 | ровно |

Главный блок — не потеря, а решение: коммит `24fdf53` от **22.08 22:11** «выключить алерты из е-магазинов UZEX — это каталог продавцов». Посуточный ряд подтверждает механику: 12 алертов 21.08 → 2 (22.08) → **ровный 0 все 8 суток с 23.08**. Это обрыв по выключателю, а не затухание.

Проверено и отвергнуто ложное объяснение: демоут е-магазинов из push существует с 01.07 (`c972851`), но алерты шли до 22.08 — значит цифру объясняет именно `24fdf53`, а не старый коммит.

**Ингест при этом ВЫРОС** — то есть срезана доставка, а не сбор:

| Э-магазин | строк W35 | строк W36 | алертов W35 | алертов W36 |
|---|---|---|---|---|
| бумага и изделия | 848 | 944 (+11%) | 48 | 11 |
| печатные услуги | 169 | 307 (+82%) | 26 | 7 |
| издательские услуги | 382 | 439 (+15%) | 18 | 2 |

**Дефект рубрики:** метрика не отличает «мы потеряли охват» от «мы намеренно срезали шум» — и записала осознанное улучшение в минус (−0.15 композита). Тот же класс, что дефект знаменателя `platform_health` из W34 (не исправлен ради сравнимости W25–W35).

**Хуже: штраф решён двенадцатью алертами на границе ступени.** `weekly_metrics.py:176-188` — `_subscore_recall` не измеряет охват, а сравнивает WoW-отношение с двумя порогами:

```python
base = 6.8
if ratio < 0.7:   base -= 1.0
elif ratio > 1.3: base += 0.5
```

То есть sub-score физически принимает всего три значения — **5.8 / 6.8 / 7.3**. В этом году в ряду других и не встречалось. А наше отношение `258/385 = 0.6701` при пороге `0.70`: до несрабатывания штрафа не хватило **~12 алертов**. Полновесный −1.0 балла (−0.15 композита) назначен попаданием в ступеньку, а не измеренной потерей охвата.

Проверка того же числа с возвращённым намеренным вырезом: `(258+72)/385 = 0.857 > 0.7` → recall был бы **6.8**, композит **6.6** вместо 6.4.

## Идеи /deep-think — что делать дальше

Три темы разобраны отдельно. Ниже — только то, что проверяемо; для каждого пункта указано, как именно проверить, и уровень риска по правилам рутины.

### И1. Закрыть разрыв «сигнал есть — действия нет» (корень всех трёх инцидентов)

Разбор показал, что детекторы у нас сильные, а слой между «система знает» и «человек сделал» — однократный. Проверено по коду:

- **Ошибка не доезжает до записи прогона.** `crawler/adapters/base.py:36-49` — контракт `fetch()` «never raises»: 400 ловится, пишется в `last_error`, возвращается `[]`. `crawler/core/runner.py:147` вызывает `log_source_result(sid, len(result))` **без `error=`**, потому что ветка исключения (`:142`) недостижима. **Проверено на живых данных:** прогон с 400 записан как `error_sources: [] , etender: {'fetched': 0, 'errors': []}` — байт в байт как здоровый пустой источник; следующий прогон после фикса — `fetched: 627`. То есть даже поздний разбор по БД не смог бы отличить поломку от тишины апстрима.
- **Все три сторожа edge-triggered.** `freshness_watchdog.py:259` (`new_silent = [... not in prev]`), `funnel_watchdog.py:541` (сравнение по набору видов тревог), `zero_result_tracker.py:144-160` («alert exactly once per zero streak»). Ни у одного нет ни повтора, ни эскалации по возрасту, ни примитива подтверждения.

### И2. Починить рубрику так, чтобы падение перестало требовать объяснений

Проверено, что «сравнимость W26–W35», ради которой в W30 и W34 отказывались править формулу, **защищает ряд, которого уже нет**: композит с W26 считается с ручной подменой 25%-го слагаемого (AI-судья вместо детерминированного precision). Арифметика на W35 сходится: по буквальной формуле вышло бы 5.74 (и это же число названо в W35 как «5.7»), опубликовано 7.0.

Предлагается узкий v2, считаемый параллельно с v1 (*риск: безопасная*, пока v1 остаётся авторитетным):
1. **Снимок политики доставки в недельный JSON** (`no_push_sources` + sha `notifier.py`) — чтобы пересчёт прошлых недель не подделывал историю сегодняшним списком.
2. **`recall` по общей поверхности доставки** — WoW только по источникам, бывшим on-push в обе недели.
3. **`link_integrity` не меняет формулу, но обязан нести `coverage`** (`checked`, `reachable_universe`, `alert_link_share`), и рутина печатает «link 6.0 при покрытии N%».
4. Знаменатель `platform_health` (`retired_sources.yaml`) — *риск: рискованная*, требует решения Данияра о составе; выносится отдельно.

**Главный тест бэкфилла:** политика менялась ровно дважды (`c972851` 01.07, `24fdf53` 22.08), значит v2 обязан совпасть с v1 **на всех неделях, кроме W27/W28 и W36**. Расхождение где-то ещё = баг бэкфилла, а не находка.

Отдельно (и **не** в одном заходе с предыдущим, иначе сломается этот инвариант): ступенька `ratio < 0.7` в `_subscore_recall` заслуживает замены на непрерывную функцию — сейчас 12 алертов на границе стоят целого балла.
