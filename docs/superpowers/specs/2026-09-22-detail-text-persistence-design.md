# C2 — сохранение detail/specification между обходами

## Проблема

У API-источников с `detail_fetch` предмет закупки попадает в `search_text`
только в первом обходе: маркер `max_seen_id` не даёт снова вызывать detail API,
а повторный list-upsert записывает короткие поля карточки поверх обогащённого
текста. У `UZEX Предквалификации` аналогичный риск: позиции лежат в
`extra_info.lots`, но следующий list-upsert заменяет `search_text` категорией.

## Решение

* У источника появляется явный opt-in `detail_persistence`.
* Detail-текст обычных двухшаговых API хранится в служебном
  `extra_info._detail_text`; позиции предквалификаций остаются в
  `extra_info.lots`.
* Перед upsert хранилище читает `extra_info` только для opted-in источников и
  восстанавливает предмет в новом `search_text`, сохраняя служебный payload.
* Служебные ключи с `_` никогда не рендерятся в Telegram.

Это не добавляет миграций, не делает повторных сетевых detail-запросов и не
меняет обычные источники.

## Контракт

1. Повторный list-crawl того же лота сохраняет его detail/specification в
   `search_text`.
2. Обычная metadata из list-ответа продолжает обновляться.
3. Detail-payload не виден в alert и не создаёт новых AI-вызовов.
4. Без opt-in тендер и его `search_text` не меняются.
