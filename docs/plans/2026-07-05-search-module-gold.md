# «Золото» каждой площадки + архитектура модуля поиска (2026-07-05)

Проверка полноты данных для цепочек «позиция→лот→аукцион→договор» по каждой площадке, live-зонды с нашими ключами. Дизайн-док (без внедрения). Каждый факт проверен, помечено что НЕ работает.

## Полнота данных по площадкам — вердикты

### 1. ETender — ПОЛНАЯ цепочка ✅ (эталон)
Сделка↔лот сшивается на 100% (1569/1570, ключ = короткий id из URL). Итог уже измерен: 19 победных print-контрактов, 11 алерчены (58% outcome-recall), 8 промахов поимённо.
**Золото:** сами победные лоты = ground-truth разметка для обучения фильтра.

### 2. Cooperation — цепочка ЕСТЬ ПО КЛЮЧАМ, но не сшита ⛏️ (главная находка)
- Лот несёт `offerNumber` (из какой оферты создан). Контракт (stat-new API) несёт `lotNumber` — **но мы его НЕ сохраняем** (external_id=contractNumber, lotNumber выбрасывается). Однострочный фикс → полная цепочка **оферта → лот → контракт ПО КЛЮЧАМ**, без имён и нечётких джойнов. Никто её ещё не собирал.
- **ТНВЭД заполнен у 99.9% лотов (2998/3000)** — второй самородок, см. модуль поиска ниже.
- Заказчик лота: публично НЕ существует (проверено с токеном, 05.07) — честный предел.

### 3. XT-Xarid / Hayotbirja — post-mortem аукционов ⛏️
`get_proc` ЗАКРЫТОГО reduction отдаёт анонимно: **победителя** (последняя ставка в `log_bet`: team_name + ИНН!), всех участников (имена+ИНН+timestamps), `contract_id`, «Сумма залога».
**НЕ работает:** суммы ставок в log_bet МАСКИРОВАНЫ (3-значные обрезки «860»/«012» — проверено против стартовой цены 117.6М; это не цены). Ценовая динамика доступна только LIVE через листинг `last_price` (⚔️ watch_our_lots уже пишет time-series).
**Золото:** ночной post-mortem закрытых print-reductions → авто-реестр конкурентов (кто участвует/выигрывает, с ИНН) + win-rate по товарным группам. Латентно уже есть в API — нужен только сборщик.

### 4. Ebirja — золото зарыто в собственной БД ⛏️
Победитель/цены/скидка СОБИРАЮТСЯ detail-фетчером, но складируются строками в `search_text` («buyer | winner | lot | contract | start:N | discount:N%»). **Backfill-парсер по 2.8k существующих строк** (без рефетча) → структурные поля → договорная аналитика ebirja открывается бесплатно. Типы в префиксах: XA=аукцион, XO=отбор, XD=э-магазин.

### 5. UZEX — цепочка невосстановима, но intel полный ✅/❌
Результаты: 2127 строк, 100% с победителем и ценой. Исходные лоты — закрытые каналы (калибратор 06.06: 60/60 отсутствуют в открытых фидах). **Не recall-инструмент, а прайс-разведка**: скидки (8.6% медиана print) + имена конкурентов.

### 6. TG-лиды — цепочка уходит с площадки → CRM-join ⛏️
Сделка происходит вне биржи → на площадке следа нет. **Золото: join с Bitrix24** (MCP подключён): лид алерчен → появилась ли сделка в CRM (по телефону/имени/дате) → настоящая конверсия лидов, замыкает контур для 63% всех алертов.

## Архитектура модуля поиска («находить ВСЕ нужные лоты»)

Сейчас: keyword-regex (ru) → AI. **Слепое пятно доказано:** узбекоязычные названия — «Рўйхатга олиш журнали» (регистрационный журнал, ТНВЭД 4820) в БД, но keyword-ами не пойман, слова «журнал» в STRONG нет.

### Трёхслойный scope-фильтр (нестандартный ход = слой кодов)
```
Слой 1: ТНВЭД/ЕНКТ коды  — детерминированный, ЯЗЫКОНЕЗАВИСИМЫЙ    (новый)
        print-профиль: 4802/4810/4811 (бумага), 4817 (конверты), 4819 (картонная упаковка),
        4820 (журналы/тетради/бланки), 4821 (этикетки), 4901-4911 (печатная продукция)
        исключая 4818 (гигиеническая бумага — не наш профиль).
        Покрытие: cooperation 99.9%; проверить xt-xarid good_maps (ЕНКТ) и etender OKED.
Слой 2: STRONG keywords  — ru + ДОБАВИТЬ uz-кириллицу/латиницу     (расширить)
        (журнал/jurnal/дафтар, гувоҳнома, блокнот-варианты…) — майнинг из слоя 3
Слой 3: AI relevance     — как есть (арбитр пограничных)
Правило: (Слой1 ∪ Слой2) → Слой3. Код 48xx/49xx попадает в AI даже при нуле keyword-хитов.
```

### Labeled-data flywheel (самообучение поиска)
Победные контракты (ETender 19 + UZEX 54 + Coop 5 + ebirja после backfill) = растущий ground-truth positive set. Еженедельная рутина: n-gram/код-майнинг по нему → «кандидаты в STRONG/ТНВЭД-список» → подтверждение Данияром → фильтр растёт от реальных исходов, не от догадок.

### Server-side фильтры (полнота без пагинационных потолков)
Vendor-фильтр birja доказан (watch_our_lots). Проверить на тех же ref'ах фильтры по категории/коду — если есть, сбор print-scope станет полным на стороне сервера (никаких «первые N страниц»).

### Outcome-контур (цепочки как постоянный процесс)
1. Coop: сохранить `lotNumber` в контрактах (1 строка) → key-chain оферта→лот→контракт.
2. Ebirja: backfill-парсер search_text → структурные winner/discount.
3. XT: ночной post-mortem закрытых reductions → outcomes-таблица + реестр конкурентов (ИНН).
4. ETender: конверсия «алерчен→контракт» в недельную рутину (join готов).
5. TG: Bitrix-join конверсии лидов.
→ Одна таблица outcomes на все площадки: считаем не «сколько алертов», а «сколько ДОГОВОРОВ поймали/пропустили» — метрика бизнеса, не краулера.
